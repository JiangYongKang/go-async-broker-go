# go-async-broker-go

一个可在本地运行的异步消息投递与任务处理引擎。用本地文件存储模拟消息
代理与消费状态，使消息在生产、投递、重试、死信与重启恢复各环节的结果
一致、可解释、可验证。

## 结构

```
broker/
  types.go    消息模型、状态机、可区分错误、配置
  store.go    状态快照的原子持久化（tmp + fsync + rename）与恢复
  broker.go   引擎主体：生产、按组有序投递、确认/拒绝、重试退避、死信、背压
  offset.go   消费位点提交（严格单调，回退拒绝）
  outbox.go   事务性发件箱：业务写入与待发消息的原子提交与崩溃重放
  dedup.go    消费端幂等器：抑制重复投递造成的重复副作用
  replay.go   死信重放：按批/按分组重回投递链路，幂等、保序、可恢复、可追溯
```

所有状态文件位于 `Config.Dir`：`state.json`（消息、位点、重放记录与
生命周期事件）、`outbox.json`（提交意图日志）、`biz.json`（模拟业务
库）、`dedup.json`（消费端去重记录）。

## 投递语义

- **至少一次**：消息先落盘再对外可见；已投递未确认（inflight）的消息在
  进程重启后一律回到 pending 重新投递，不会丢失。
- **组内有序**：同一 `Group` 同一时刻至多一条 inflight；投递以"组头"
  为单位——只允许组内最小序号的 pending 消息投递，组头在退避等待时
  全组等待。确认或重试完成前，同组后续消息（含重放回队的消息）不会
  发出，因此正常投递、重试与死信重放过程中组内顺序稳定，不受并发
  消费影响。
- **确认/拒绝的确定性**：
  - `Ack` 未知消息 → `ErrUnknownMessage`
  - `Ack` 已确认消息（重复确认）→ `ErrAlreadyAcked`
  - `Ack` 其他非 inflight 状态 → `ErrNotInflight`（携带当前状态）
  - 三类原因可用 `errors.Is` 区分；失败不会改变消息现有状态。
- **消费端幂等**：至少一次语义下重复投递不可避免，`Dedup.ProcessOnce`
  以持久化记录保证同一消息的副作用（如计费）只生效一次，重复投递返回
  `ErrDuplicate`。

## 重试与死信规则

- `Nack(id, retryable, cause)`：
  - `retryable=true`：按指数退避重投，第 n 次等待
    `min(BackoffBase << (n-1), BackoffMax)`；当已投递次数超过
    `MaxRetries` 时进入死信，判定依据 `DeadReason=retry_exhausted`。
  - `retryable=false`：不消耗重试次数，直接进入死信，判定依据
    `DeadReason=non_retryable`。
  - 死信重放后的再次死亡使用可区分的原因：`replay_retry_exhausted`
    （重放后重试再次耗尽）与 `replay_non_retryable`（重放后再次被
    判定不可重试），与首次失败明确区分。
- 每次判定都记录在消息的 `ErrorClass` / `DeadReason` / `LastError`
  字段上，可通过 `Get` / `DeadLetters` 观测；死信消息保留在存储中，
  不会被静默丢弃。

## 死信重放

根因修复后，可把死信重新投入正常投递链路，重放后的消息与普通消息走
完全相同的投递、确认、重试退避、再次进死信流程。

- **用法**：
  - `ReplayDead(ctx, ids)`：按一批消息重放；
  - `ReplayDeadGroup(ctx, group)`：重放指定分组当前的全部死信；
  - 返回的 `ReplayResult{ReplayID, Replayed, Skipped}` 说明哪些消息
    实际重回投递、哪些目标被跳过及原因（`not_found` / `not_dead`）；
    - `Replays()` 列出全部重放请求记录；`History(id)` 列出单条消息
    的生命周期事件（每次进死信、每次重放，含判定原因与重放请求 ID）。
- **原死信不被抹掉**：重放是"原地转回 pending + 追加事件"，不是删除
  重建。历史 `dead` 事件保留；本次转换追加 `replayed` 事件；消息的
  `ReplayGen` 自增。再次进死信时原因是 `replay_retry_exhausted` /
  `replay_non_retryable`，并关联到发起该轮的重放请求，首次失败与
  重放后失败在本地一目了然。
- **重新获得完整重试预算**：重放时 `Attempts` 归零、退避清除，消息
  可以重新观察到与首次生产相同次数的重试机会。
- **幂等与并发安全**：状态判定、重放记录与消息转换在同一把锁内、同
  一次原子快照落盘。同一条死信被重复调用或被多个消费者并发重放时，
  只有一次会真正转换，其余返回 `Skipped(not_dead)`，不会产生第二条
  在途消息；配合 `Dedup.ProcessOnce` 可保证副作用（计费等）不重复。
- **组内顺序兼容**：重放消息分配新的全局序号、排到所属分组队尾；
  投递以"组头"为单位——分组内序号最小的 pending 消息退避未到期时，
  全组等待。因此重放消息不可能插到同组尚未处理完（包括正在退避等待
  重试）的消息前面，也不会越过组内其他待投递消息；组间互不阻塞。
- **容量兼容**：重放计入 `MaxPending`（pending + inflight）。
  `PolicyReject` 下容量不足立即返回 `ErrBrokerFull`，不留下任何记录、
  不改动死信状态；`PolicyBlock` 下阻塞至容量释放或 ctx 取消。重放
  意图一旦落盘接受，即视为已提交，崩溃恢复补齐时不受容量限制（与
  outbox 已提交事务不丢消息的策略一致）。
- **崩溃恢复确定性**：重放记录先落盘后生效，并记录每条目标是已重放
  还是已跳过。重启时未完成的记录幂等补齐：`Replayed` 列表中的消息
  绝不二次重放（即使它在此期间又一次进死信），其余仍是 dead 的目标
  被补齐、其他状态记为跳过。整批重放不会出现"重放两次"或"丢失"。

## 原子提交与恢复（事务性发件箱）

`Outbox.AtomicCommit(opID, bizOps, msgs...)` 按以下顺序执行，每步幂等：

1. 意图（业务写入 + 待发消息）写入 `outbox.json` 并落盘；
2. 应用业务写入到 `biz.json`（按 opID 去重）；
3. 消息入队（按调用方给定的确定性消息 ID 去重）；
4. 标记意图完成并落盘。

进程在任意两步之间崩溃后，`Outbox.Recover()` 按相同顺序重放未完成
意图：已应用的业务不会重复应用，已入队的消息不会重复入队。因此不会
出现"业务已提交却丢消息"，也不会出现"消息可见但业务未提交"。
业务写入建模为可序列化的 `BizOp`（KV 写入），这是本地模拟的要求；
接入真实数据库时，等价做法是把意图与业务写入放进同一事务。

## 背压与容量上限

- `MaxPending` 限制 pending + inflight 总量，内存占用有界。
- 达到上限时按 `Policy` 行为：`PolicyBlock` 阻塞生产者直到容量释放
  （或 ctx 取消）；`PolicyReject` 立即返回 `ErrBrokerFull`。
- 两种行为都确定且可观测（`Pending()`），已接收的消息不受影响、不丢失。
- 已提交事务（outbox）的消息不受上限约束，保证已提交事务不丢消息。

## 消费位点

- `CommitOffset(group, offset)` 只接受严格单调前进的位点；回退或与已
  提交值相同（崩溃恢复后的重复提交）都返回 `ErrOffsetRegression`，
  不会从中间继续或重复提交。位点与消息状态同事务落盘，重启后不丢。

## 本地验证

```bash
go build ./...
go test ./broker/ -v        # 全部单测，日志打印输入与判定依据
go test ./broker/ -race     # 并发一致性（多生产者/消费者/中途恢复/重放并发）
go run ./cmd/demo           # 端到端演示：原子提交/顺序/重试/死信/重放/崩溃恢复
```

测试以失败与边界链路为主，覆盖：重复投递与消费端幂等、重试耗尽进死信、
不可重试错误直接进死信、确认/拒绝的三类可区分错误、位点回退拒绝、
背压阻塞与拒绝、崩溃恢复（inflight 重投、outbox 三种崩溃点重放、
损坏状态文件明确报错）、并发下组内顺序稳定与恰好一次计费，以及死信
重放：按批/按分组重放、重复与并发重放幂等、与同组退避消息的顺序、
容量拒绝与阻塞、重放中途重启的确定结果、重放后再次耗尽与首次失败的
原因可区分。
